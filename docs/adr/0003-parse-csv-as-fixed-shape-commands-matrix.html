kraken: CSV parser shape decision matrix

The order routing stage turns one UDP datagram into one typed command. The input grammar is small: three record markers and fixed field counts. The decision is how much generic CSV machinery to put between those bytes and the typed command variant.

Assumptions

  • Inputs are well-formed exercise commands. The provided test/*/in.csv rows match the documented command shapes, and EXERCISE.md says hidden tests use the same format. The decoder treats this as a precondition: helpers assert on violation instead of returning kraken::result errors.
  • The wire grammar is closed. The exercise defines N, C, and F only; there is no quoted field, escaped comma, multiline record, or schema extension requirement.
  • Malformed data is not a primary design target. The errors::parse_error payload and the rejection branch in session.cpp stay defined so a future producer can re-enable structured rejection, but the CSV decoder under the current contract never reaches them.
  • Order routing is on the processing path. Avoiding avoidable allocation and broad parser dependencies matters more than accepting CSV dialect features the exercise does not use.
  • Delivery time is constrained. The submission window is tight. Where a stock library helper short-cuts the implementation, the implementation accepts the helper even at a measurable performance cost and flags the call site for a perf-driven follow-up. This premise governs the splitter sub-decision below the main matrix; the parser-shape decision itself does not bend on it.

Decision

Decision: fixed-shape string_view split. The parser follows the exercise contract rather than implementing a general CSV dialect: switch on the first byte, split the expected field count for that marker, and parse into strong command types.

The well-formed input assumption decides the trade-off. The internal helpers (split_fields, parse_number, parse_side, parse_symbol, and the per-marker decode_* functions) take the grammar as a precondition, return their domain types directly, and assert on violation via KRAKEN_ASSERT. The decoder boundary keeps its kraken::result<command> return so a future non-CSV decoder can carry richer errors; under the current contract the CSV path always yields a value, and the errors::parse_error payload plus session.cpp rejection branch remain defined for that future producer.

Sub-decision: splitter implementation. Within A, the splitter is boost::algorithm::split into a std::vector<std::string_view> rather than a hand-rolled cursor or a non-allocating boost::tokenizer. The trade is one heap allocation per parse against fewer lines, fewer edge cases to argue about, and faster sign-off under the submission deadline. The call site carries an IMPROVEMENT: comment naming the lazy follow-ups, and the cost is tracked in Open Questions above. The parser-shape decision is unchanged; the time-pressure assumption bites only on this sub-call.

kraken: order-book data structure decision matrix

The matching engine needs a per-symbol book that preserves price-time priority, exposes top-of-book aggregates, and supports cancels by (user, user_order_id). The decision is staged: pick the smallest structure for the first passing implementation, then choose the optimization structure now that behavior is covered by the suite.

Assumptions

  • The first implementation is already passing the suite. The initial target was correctness and clarity under the provided harness.
  • The matching engine is the primary review surface. A reader should be able to check price-time priority and event ordering without first auditing custom memory management during behavior bring-up.
  • Price levels are sparse and not pre-bounded. The input can introduce new prices without a known tick range or per-level depth distribution.
  • The next work is optimization. With the behavior suite green, the next iteration can spend complexity on direct cancellation and avoiding per-order placement allocation.

Preallocated vectors + tombstones Bounded contiguous storage per level; cancels mark entries inactive and matching skips them. D. Price-time semantics Map order gives price priority; vector append gives time priority within a level. Natural fit: list order is arrival order once the side map finds the price. Works if tombstones are skipped consistently. Works, but iteration must correctly cross block boundaries while preserving arrival order.
Implementation and test surface Standard containers keep tests focused on behavior, not allocator and node invariants. Boost handles list unlinking, but pool sizing, pointer lifetime, and index consistency need focused tests. Simple at first, then grows rules for tombstone cleanup and capacity overflow. Custom block chaining, reclamation, and iterators create the largest local bug surface.
Cancel latency Scans resting orders across books and sides because the cancel command carries no symbol, side, or price. Direct index lookup plus intrusive unlinking gives true O(1) cancellation. A direct handle can tombstone the entry in O(1). A direct handle can tombstone in O(1), but block-active counts and reclamation add branches.
Placement allocation A new price level or growing vector can allocate. Acceptable under the harness, but not a production hot-path target. A preallocated pool can make order placement allocation-free after startup. Safe operation depends on reserving enough capacity for every active level; exceeding it reallocates or fails. A preallocated block pool can grow active levels without heap allocation.
Sparse and unknown prices New prices create entries only when they appear. Also handles sparse prices; each active level owns a list. Either reserves too much for prices that never trade or risks resizing when an unexpected level appears. Handles sparse prices if the global block pool is sized for total active orders.
Sweep locality Good enough for scenario-sized levels; vectors are contiguous, but front erasure can move survivors. Pointer chasing can miss cache during deep sweeps. Best locality: contiguous scans suit hardware prefetch. Mostly contiguous within each block, with occasional pointer jumps.
Reader clarity A reviewer can verify the structure from the type aliases and a small amount of code. Readable with Boost knowledge, but intrusive hooks and ownership rules become part of the review. Easy to explain until tombstones and compaction enter the path. The implementation explains storage mechanics more than matching behavior.
Upgrade path Leaves a clean local replacement path: add a cancel index, then swap level storage after benchmarks. Good production fallback once zero-allocation or cancel latency dominates. Capacity assumptions make it a poor intermediate step for this protocol. Good later option if benchmarks show sweeps dominate and a block pool can be sized safely.

Decision

Decision: sorted maps of vectors for the first iteration; intrusive lists plus pool for the optimization iteration. The submitted behavior-first implementation keeps side-specific std::map<price, std::vector<order>> containers: descending for bids, ascending for asks, and append-only within each price level until matching or cancellation removes entries.

The first-iteration criteria were submission fit, implementation surface, and reader clarity. The current structure made price-time priority visible and kept tests centered on observable matching behavior. Now that the suite is passing, the optimization criteria move the decision toward intrusive lists plus an object pool.

The list+pool option targets the two costs the map+vector implementation deliberately accepted: cancellation scans and placement allocation. A direct (user, user_order_id) -> order* index plus intrusive unlinking gives direct cancellation, while pool-owned nodes remove per-order heap allocation. Paged blocks stay as a later candidate if sweep locality becomes the dominant measured cost.

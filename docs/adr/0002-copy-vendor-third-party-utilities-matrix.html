ADR-0002: dependency acquisition decision matrix

Companion to ADR-0002. Every third-party dependency in the build is in scope: header-only utilities for the lab vocabulary and compiled libraries used by domain code, tests, and benchmarks. The decision is which single mechanism brings all of them into the build.

Assumptions

  • Vendor everything: no third-party dependency comes from system packages.
  • Two source forms only: public GitHub upstreams and code written in this repository. Binary drops, tarballs, raw URL fetches, and find_package fallbacks are out of scope.
  • Single source of truth: dependency declarations should live where the build does, in CMake.
  • One mechanism: a single acquisition path should cover both header-only utilities and compiled libraries.
  • Network at configure time: the project does not promise an offline fresh-checkout experience.
  • Pins are explicit: each dependency carries a release tag (when stable in practice) or a commit SHA.
  • Project vocabulary: libraries of types are consumed through lab:: re-exports; libraries of functions are consumed through their canonical upstream target.
Criterion A. CMake FetchContent Declare every dep in vendor/CMakeLists.txt and fetch from GitHub at configure time. B. Copy-vendor Commit selected upstream bytes under vendor/<name>/upstream/ with metadata files and a refresh script. C. Git submodules Track each upstream as a pinned submodule under vendor/. D. ExternalProject Drive download, configure, build, and install through ExternalProject_Add.
Single source of truth Pin and acquisition both live in CMake. Pins live in metadata files driven by a shell script outside CMake. Pins live in .gitmodules, separate from CMake. Acquisition lives in CMake.
Handles both tiers Same declaration shape for header-only and compiled libraries. Compiled libraries become committed buildable trees. Works for both, but cold-clone setup degrades for compiled deps with submodules of their own. Works for both, with extra plumbing for the header-only case.

One submodule per dep, plus recursive-clone discipline. Download, configure, build, install, and include-export plumbing per dep.

Reproducibility SHA or tag pin in CMake; cache populated at first configure. Exact bytes are committed. SHA pin is explicit. URL and SHA can be pinned; consumption model is build-time.

Targets are imported from build outputs; in-tree subdirectory model is lost.

Decision

Decision: A. CMake FetchContent. It is the only mechanism that expresses dependency acquisition entirely in CMake while handling both header-only and compiled libraries with the same declaration shape. The alternative that came closest -- a split with copy-vendor for header-only utilities and FetchContent for compiled libraries -- was rejected because maintaining a second acquisition system outside CMake (refresh script, metadata files, committed upstream/ trees) is a larger cost than first-configure network use.

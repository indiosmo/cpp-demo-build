kraken: dependency management decision matrix

The submission needs four small header-only utilities (strong-typedef helper, fixed-capacity callable, SPSC queue, expected vocabulary type -- see DEPENDENCIES.md). How do we bring them into the build? Constraints in play: the graded harness runs docker build then docker run against the submission, delivery is by git bundle, and the project has an interview-shaped deadline rather than a multi-year maintenance horizon.

Assumptions

  • All four utilities are header-only. No upstream build systems to plug in; the integration is "add to the include path".
  • Delivery is a git bundle. Per EXERCISE.md, the submission is shipped as a single pack file. Whatever isn't in the parent repo's history doesn't travel.
  • Network is available during docker build. The submission's Dockerfile already runs apt-get update and apt-get install for the toolchain and system libraries, so network is on. Copy-vendor is still preferred -- the bundle constraint decides it independently, and removing configure-time fetches eliminates a transient-failure axis during a one-shot grading run.
  • Versions are pinned once. No update cadence to amortise over; pick a commit per dep at vendoring time and leave it.
  • fixed_string and match / match_partial are not vendored. Both are small enough to be written in-house under submission/src/kraken/kraken/, so they drop out of the vendored list and the count goes from six to four.
  • All four remaining upstream licenses are permissive. MIT (NamedType), BSL-1.0 (SG14 inplace_function), BSD-2-Clause (readerwriterqueue), and CC0-1.0 (TartanLlama expected). Attribution requirements are satisfied by shipping each upstream's LICENSE inside submission/vendor/<name>/.
Criterion A. Copy-vendor Drop the upstream headers into submission/vendor/<name>/; commit a VERSION.txt with upstream URL and SHA next to each. B. Git submodules Each upstream lives at submission/vendor/<name> as a submodule pinned by SHA. C. CMake FetchContent One FetchContent_Declare per dep in the top-level CMake; sources fetched at configure time, pinned by GIT_TAG. D. ExternalProject superproject A custom CMake module orchestrates per-dep ExternalProject_Add blocks with their own download / configure / build / install steps and dependency edges into the consumer.
Network-failure surface during grade Zero. Sources are bytes in the tree by the time the Dockerfile COPYs; no fetch step can fail. Submodule contents don't live in the parent repo, so the standard COPY + cmake Dockerfile sees empty submodule directories. Fixing it requires either a host-side pre-init step before bundling or a Dockerfile rework with git + recursive checkout, both of which add their own failure surfaces. Network is available, but each configure-time fetch is a transient failure axis (GitHub flake, DNS, mirror outage) during a one-shot grading run. Same per-dep fetch surface as FetchContent; the failures land at build time rather than configure time but they land all the same.
Travels through git bundle Files in the tree pack into the bundle natively. Grader unbundles and has everything. git bundle packs only the parent repo's history. Submodule gitlinks travel, contents don't -- grader gets dangling refs. Only CMake declarations live in the tree; they travel fine. Only CMake declarations travel.
Setup cost Per dep: git clone --depth=1, copy headers, write VERSION.txt, add one add_library(... INTERFACE). Minutes. Per dep: git submodule add plus build wiring; small but introduces a "did you init?" failure mode that costs time later. Per dep: one FetchContent_Declare + MakeAvailable. Modest, but four of them. Real boilerplate per dep (download + install + glue to expose headers). Pays superproject costs for no benefit on header-only libs.
Configure / first-build time No fetch step at all. One-off fetch on submodule update --init; cached after. First configure does N git fetches over the network. Build-time fetch + extract; touches every clean rebuild and slows incremental work on a fresh build tree.
Version pinning Exact bytes are committed. Reproducible by construction; no SHA to verify. Gitlink pins the SHA. Reproducible if the upstream URL still resolves. Pinned by GIT_TAG <sha>. Reproducible if upstream is up. Pinned by URL + SHA. Same upstream-availability caveat.
CMake complexity One INTERFACE target per dep with target_include_directories. Nothing else. Comparable to copy-vendor, plus a guard for "submodule directory empty" with a clear error message. Modern CMake idiom, well-supported, but each block needs the right flags (GIT_SHALLOW, SYSTEM, EXCLUDE_FROM_ALL) to behave. Real engineering: per-dep targets, dependency edges between the external project and the consumer, exported include dirs. Appropriate for non-trivial libraries; overkill here.
Cold-clone local dev Clone, configure, build. Nothing else. One extra step: --recurse-submodules or post-clone submodule update --init. Easy to forget; pleasant error messages mitigate but don't eliminate. First configure needs network. First build needs network.
Updateability Manual re-copy if an upstream fix is worth taking. Fine for "pin once". cd vendor/<name> && git checkout <sha>; commit the gitlink bump. Bump the SHA literal; reconfigure. Bump the SHA; rebuild.
Repo size impact Adds the source bytes. Six header-only libs together are well under a megabyte. Pointers only. No sources in tree. No sources in tree.

Decision

Copy-vendor. The two hard constraints -- offline Docker grade and clean git bundle delivery -- both point at it, and they are the only rows that genuinely could blow up the submission. Every other option fails at least one of them; the wins they offer (smaller repo, easier updates) carry no weight on an interview timeline where dependencies are pinned once.

Mechanics: per dep, git clone --depth=1 the upstream into a scratch directory, copy just the public headers into submission/vendor/<name>/, write a one-line VERSION.txt with the upstream URL plus the commit SHA, declare one add_library(<name> INTERFACE) in the vendor CMakeLists.txt, and re-export under submission/src/kraken/kraken/<role>.hpp per the alias rule documented in DEPENDENCIES.md. The VERSION.txt is the audit trail -- a reader can match the vendored bytes to an upstream commit without git archaeology.

Considerations for the others: submodules are out because a git bundle doesn't carry submodule contents and the standard COPY-then-cmake Dockerfile doesn't init them; fixing either end adds more moving parts than the alternative removes. FetchContent is the option a longer-lived project would pick -- bump-a-SHA updates are nice, and the build environment does have network -- but every configure-time fetch is a transient-failure surface during a one-shot grading run, and copy-vendor removes that surface entirely. An ExternalProject superproject is the right tool for libraries that bring their own build systems and need custom configure/install integration; it is the wrong tool for four header-only utilities.

Future polish if we ever wanted to keep the easy-update property: FetchContent_Declare with FETCHCONTENT_SOURCE_DIR_<name> pointed at the vendored tree gives the bump-a-SHA flow on top of offline-by-default. Not worth wiring during this submission; worth noting as a no-regret upgrade path.

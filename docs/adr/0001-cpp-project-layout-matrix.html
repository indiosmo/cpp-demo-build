ADR-0001: C++ project layout decision matrices

Companion to ADR-0001. Four coupled sub-decisions: source-tree shape, where the tooling and build-configuration files live, how the Docker copy boundary is handled, and how project() calls are organized once a repo-root CMake exists. Decisions are sequenced -- each one constrains the next.

Assumptions

  • Library and application count: at least four libraries (a utils library plus order routing, market data, and matching engine) and one application.
  • Docker pipeline stability: the grader copies only submission/ and will continue to.
  • Test and benchmark tooling: Catch2 and Google Benchmark are the committed choices.
  • No second C/C++ consumer at the workspace root: the repository is self-contained, and nothing outside submission/ is or will be C/C++.
  • Zero-warning build policy: the team treats configure warnings as defects and builds to zero warnings.

1. Source-tree layout

The starting point (initial commit) is a six-line submission/CMakeLists.txt with one add_executable over src/main.cpp and nothing else. The brief asks for a production-style layout, so the comparison is between staying flat and one of two structured shapes that grow naturally.

Decision -- Matrix 1

Decision: C. Aggregated. The brief rules out the flat status quo, and between the two structured shapes, the DRY-ness and tooling-scope rows decide it. Module-colocated repeats the find_package dance for Catch2 and Benchmark in every module and turns every linter or formatter script into a per-module exclusion list; with at least four libraries on the way, both costs compound rather than amortize.

Workspace-level files -- CMakeLists.txt, CMakePresets.json, .clangd, .clang-format, cmake/, build.sh -- can live inside submission/ or at the repository root, or be split between the two. None of these existed at the initial commit, so this is purely about where to introduce them.

Repo-root-owned All configs at the repo root; the repo-root CMake delegates into submission/ via add_subdirectory(). C. Split Editor configs (.clangd, .clang-format) at the root; CMake stays inside submission/.

Decision -- Matrix 2

Decision: B. Repo-root-owned. With the no-second-consumer assumption in place, the clangd-reach row no longer separates B from C; B's remaining edge over Split is CMake invocation ergonomics -- cmake -S . and cmake --preset=... run from the repo root rather than from a source path one level down.

The call stands but by a narrower margin than the matrix originally framed. B's coordination cost is real: two project() calls and two language-standard declarations have to stay in sync. Matrix 4 manages this cost. Split is the clean fallback if that coordination ever becomes a problem.

3. Docker pipeline handling

The graded build copies submission/ and builds it. The development build wants warnings, sanitizers, and other hardening flags that are intentionally not in the graded environment. The question is whether to honor the Docker boundary as-is (keep submission/ independently buildable) or expand it (have Docker copy the whole repo and build from there with the same flags as local).

Submission-standalone submission/CMakeLists.txt is dual-mode (if(NOT PROJECT_NAME)); Docker still copies only submission/. C. Single-tree (drop the submission/ boundary) Collapse the split: move everything to the repo root and adjust the Dockerfile to copy the relevant subset.

Decision -- Matrix 3

Decision: B. Submission-standalone. This is the only sub-decision where the call is close on raw axes, so the weights are on and the criterion that decides it gets to say so. Flag separation is the heaviest criterion because it is the entire reason the development build is configured differently from the graded build; an option that does not preserve that separation is a different design, not just a different organization. B's faithfulness to the grader holds because the pipeline copies only submission/ -- under that premise, a developer's cmake submission/ and the grader's view coincide exactly.

The runner-up is Pipeline-rooted, and what would flip the call is a graded environment that ran the same flags as development -- then the boundary serves no purpose and collapsing it is the simpler design. Single-tree scores well on CMake simplicity but throws away the flag separation for nothing in return.

Cost paid: submission/CMakeLists.txt carries an if(NOT PROJECT_NAME) shim, and a few values (CMake minimum version, language standard) are declared in both root and submission/. Matrix 4 manages that duplication.

4. project() placement

With Matrix 2 putting CMake at the root and Matrix 3 keeping submission/ independently buildable, project() must be callable from submission/CMakeLists.txt when it is the top level. Three ways to organize the project() calls.

Criterion A. Dual-mode Two project() calls: one at the repo root, one inside the if(NOT PROJECT_NAME) branch in submission/. B. Submission-only One unconditional project() in submission/CMakeLists.txt; the repo-root CMake has none. C. Submission-only + workspace stub Real project() in submission/; a dummy project(workspace) at the root suppresses the warning.
CMake configure warnings on the root build Silent: a real project() sits at the configured root. Configure prints "No project() command in top-level CMakeLists.txt"; the warning will be raised on every run. Silent, because the stub claims the role.
CMake duplication (lines of repeated project() declaration) One repeated project() declaration. Names and language settings have to stay aligned by convention. Zero duplication. A stub plus a real declaration; same line count as A, with one of the two carrying no semantic content.
Semantic correctness at each build root (every entry point is a real project, no dummies) Both build roots declare a real project named after what they actually build. The submission build root is correct; the workspace root is silent because nothing builds when invoked there directly. Defensible but unconventional. The workspace root pretends to be a project it is not. A reader sees project(workspace) and has to learn that it is a no-op.
Idiomatic ordering of include(CompilerFlags) and include(CTest) relative to project() Each CMake calls project() before the includes that need a known language. No special casing. The root CMake needs CompilerFlags and CTest to act on the submission's languages, but cannot include them at its own scope without a project() call. Forces awkward workarounds (includes inside add_subdirectory's scope, or after-the-fact propagation). The stub provides the language context; includes work in their natural order.

Decision -- Matrix 4

Decision: A. Dual-mode. The duplication that B avoids is one line of project() declaration; the cost B pays for that saving is a permanent configure warning -- a defect under the zero-warning policy, not a nuisance to suppress -- and a contorted ordering of CompilerFlags and CTest includes. The workspace-stub option (C) buys silence at the cost of lying about what the root build is, which is the worst trade of the three.

The single line of duplication in A is structurally required by the Docker boundary set in Matrix 3 -- it is what makes both build roots semantically honest.

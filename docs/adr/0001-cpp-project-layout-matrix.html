ADR-0001: C++ project layout decision matrix

Companion to ADR-0001. The decision compares three repository shapes for matching-engine-lab: a flat executable, module-colocated tests and benchmarks, and root-level aggregated trees.

Assumptions

  • Project identity: the repository is a C++26 matching-engine lab with its project root at the repository root.
  • Modules: the project has utility, order-entry, matching-engine, market-data, server, and client surfaces.
  • Tooling: Catch2, Google Benchmark, CTest, formatting, and static-analysis workflows should have stable top-level paths.
  • Growth path: adding a module, executable, benchmark, or integration test should be additive.
Criterion A. Flat single-target One executable target owns the behavior. B. Module-colocated Each module owns its source, tests, and benchmarks beneath one directory. C. Root-level aggregated Sibling src/, test/, benchmarks/, and vendor/ trees.
Growth A second library or executable forces a restructure. New modules are additive. New modules, tests, benchmarks, and applications are additive.
Tooling scope Simple only while the project is tiny. Production-only tools need per-module exclusions for nested tests and benchmarks. Tools target src/, test/, benchmarks/, or vendor/ directly.
CMake reuse No durable place for shared test or benchmark setup. Each module repeats some dependency setup. Test and benchmark dependencies are found once per tree.
Module locality Local because there is only one target. A module's artifacts live together. A module can span sibling trees.
Portfolio readability Reads as a prototype. Readable, but less aligned with common root-level C++ lab structure. Makes the main project surfaces visible at the repository root.
Install-ready headers No library header convention. Can use stuttering public header trees per module. Can use stuttering public header trees per module and map them to an install prefix.

Decision

Decision: C. Root-level aggregated. The project uses root src/, test/, benchmarks/, and vendor/ trees. The small locality cost is accepted because the build, tooling, and portfolio orientation are clearer.
